# Parallel SD-LoRA lineage publication closeout — 2026-09-14

Status: **historical closeout / rationale only**. Current behavior lives in `project-agent-operating-principles.md` and `scenario-trigger-registry.md`.

## Why this closeout exists

Two concurrent Agents worked in nearby SD-LoRA acceleration and state-representation namespaces. The work shared an umbrella name, but the scientific treatments were not the same.

During reconciliation, a second publication path and a second lineage index were close to becoming co-equal authorities.

The durable lesson is: **parallel work that shares a family name must be reconciled by scientific identity and semantic ownership before implementation, not after duplicate pages or PRs already exist.**

## What changed in the operating model

1. Before the first substantial implementation write, search live PRs/branches/worktrees by semantic target and reader problem, not only by filename overlap.
2. Resolve each scientific line by research question/treatment semantics, maintained state representation, frozen branch/head, and plan/evidence root.
3. Treat umbrella shorthand as a search alias, never as treatment identity.
4. If two reconciliation/index artifacts exist, select one current integration path, absorb unique sibling invariants/tests, and keep the sibling historical/read-only.
5. Keep publication provenance internally consistent: declared upstream authority, code/data source, and reader-facing evidence links must point to the same integrated source.

## What was intentionally not preserved

This closeout does not store current CI state, Preview/Production deployment IDs, temporary branch/worktree paths, local ports, process IDs, or transient PR readiness. Those are use-time facts and must be re-read live.

It also does not create a second scientific authority for either SD-LoRA treatment. The experiment-side lineage/evidence chain remains authoritative for scientific claims.

## Future-Agent test

A new Agent should now be able to answer, before editing:

- Are these two artifacts the same treatment or only in the same family?
- Is there already a PR/worktree solving the same reader problem?
- Which reconciliation/index is the one current integration path?
- Do the website source links and declared upstream authority actually agree?

If any answer is unclear, the next safe action is read/reconcile, not another implementation branch.
