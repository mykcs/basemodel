# Intelligence UI：研究理解与严格对照的设计标准

**状态：CURRENT · BaseModel 项目专属内容与比较规则（2026-10-30）**  
**适用：**研究方法、论文、机制、实验与模型的解释和对照，尤其是 SEED × OpenEVO。它定义**读者需要看懂的关系与信息规则**，不是新的 CSS 设计系统。  
**一句话目标：**让读者先直接看见真正相同的研究问题和操作，再准确看见实现差异、隐含假设、证据强弱与可证伪条件；不用猜，也不需要跨列补全文义。

## 0. 设计所依赖的阅读顺序

**共同范式 → 对齐的具体操作 → 实现机制 → 方法论假设 → 证据／未知 → 可验证的研究判断。**

先给没有上下文的读者一个完整的 L0 方向，再给 L1 共同框架和关键差异；L2 承载可操作机制、例子与必要数学；L3 按需查看论文、实现、冻结实验、历史版本和复现材料。不能把会改变结论的证据边界藏在 L3。

对当前 SEED × OpenEVO Flow，外层先对齐 Stage 1「外部经验引导的能力初始化」与 Stage 2「内部反馈驱动的持续演化」，内层再讨论 SFT、OPSD、GRPO、OPD、LoRA、SD-LoRA、Memory、Skill、Agent 等技术。当前 Flow 的具体形态是**两个阶段、九组对应操作（5+4）**；九组是该路线的内容事实，不是所有比较页必须套用的模板。

## 1. Intelligence UI 的 11 条内容原则

### 01. 共同范式先于技术细节

先回答「两边在做什么相同的事」，再回答「各自怎么做」。不要从 SFT/OPSD、优化器名称或论文术语开场，逼读者自行归纳两边所属的共同问题。

### 02. 同一概念必须逐字相同

相同抽象层级下，操作名、角色名、字段标签及真正共同的说明，**左右逐字相同**。例如两侧都叫「采集 WebShop 任务轨迹」；不能一边叫「采集轨迹」，另一边叫「Qwen 执行 WebShop」。如果语义确实不相同，先拆出可共享的上位概念，再在具体机制处表达差异；不能为凑一致而改写科学事实。

### 03. 通用角色在外，可替换实现放在内

先告诉读者「外部高能力教师模型 API」是什么角色，再在相同位置分别注明具体实例，例如（GLM-5.2）与（MiniMax-M3）。供应商、模型代号或当前配置不应取代概念角色。

### 04. 同一属性必须双向对称说明

一边出现的可比属性，另一边也必须说明。例如 Stage 2 是否调用 Stage 1 外部教师，两边都显式回答；不得用一边的留白制造不存在的区别。确实只有一方具备的能力，另一方明确写「没有／不适用／未报告／尚未核实」，并区分这些状态，不能省去字段。

### 05. 技术层级必须一致

不把不同维度的技术放成互斥选项：SFT 是监督训练方式，OPSD 与 OPD 是蒸馏相关目标／机制，GRPO 是奖励驱动的优化方法，LoRA/SD-LoRA 属于参数化与更新状态机制。它们可以结合使用，不是「四选一」。比较时分别问「学习信号从哪里来、优化什么、用什么参数化方式更新、经验保存在何处」。

### 06. 区分真实的三类关系

每个对应位置明确分为：**概念／操作相同、目标相近但机制不同、仅一方具有**。同样写「更新模型参数」不等于损失函数、梯度算法、参数保存或候选准入相同。只有证据支持时才标「相同」。

### 07. 科学陈述可追溯且版本明确

具体技术主张靠近其来源；区分：论文主张、官方代码实现、我们自己的实验计划、实际执行记录、历史版本和当前冻结方案。论文预印本不等于同行评议通过；实验计划不等于已实现；实现不等于已验证收益。不同 WebShop panel、模型、采样、预算或评测口径不能因为同框展示就宣称公平直接比较。未知仍然未知。

### 08. 展示方法论立场，而不只列工具名

为重要方法提供**方法论指纹**：它认为能力从何而来、依赖哪类反馈、什么被看作学习信号、怎样表达和保存经验、如何决定接受下一状态，以及它押注哪些前提。先解释「它认为为什么会有效」，再讲技术如何实现。

**不同思想轴不能伪装为互相排斥的学派：**

- 概率／对数概率：常是预测、损失或策略优化的**数学表达与学习信号**；
- MoE（Mixture of Experts，多专家混合）：主要是一种**模型结构与路由方案**；它自身也可使用概率门控；
- latent space（潜空间）：主要是一种**表征形式**；
- 欧式、双曲或其他几何：是**表征空间及距离／结构假设**；
- 参数、Text Memory、Skill、Agent：是**能力与经验的承载位置**。

同一研究方法可同时采用多个轴。使用动作对数概率，不足以证明作者「信奉概率学派」；论文没提非欧几何，也不足以推断它反对非欧几何。

### 09. 方法假设与证据可信度分开

分别标出「作者或方法明确采用的假设」「根据机制推断的倾向」「已有实验支持」「尚无证据／待检验」。**方法偏好**不等于我们对判断的**置信度**，更不等于真实成功概率。除非事件、样本、校准方法与不确定性定义明确，不得凭印象给「80% 信概率」「90% 更好」等数字。需要粗略判断时，使用来源明确的定性等级及其依据。

### 10. 显示可证伪条件与可能失效的边界

不只说一种方法「相信什么」，还问：**如果它的核心假设不成立，应该观察到什么失败？哪个对照实验能区分机制与偶然收益？** 用「研究假设 → 可观察预测 → 检验方式 → 可能反例 → 当前证据状态」形成可检验链条。假设性失败模式必须标为待验证，不能写成已经发生的实验结果。

### 11. 禁止互文：同槽位同标签，单侧完整可读

同一比较位置必须使用完全一致的字段名称、语义层级、顺序及必要单位／分母。**字段标签同名，不意味着具体值相同。** 不允许左侧标题是「论文方法」、右侧标题是「研究方案」却暗示两者都是「研究方法」：两侧标题应同为「研究方法」，真实来源差异则放进两侧同名的「证据来源」字段。

比较单元格不可写「同左」「同上」「亦然」「见另一边」，也不能靠一侧的空白补足另一侧含义。左侧单独读、右侧单独读、左右一起读，三种路径都应完整成立。对照后的总结区域可以明确概括差异，但不得替代两个单元格本身的完整信息。

## 2. 每一个严肃对照需要的共同字段

根据读者任务选取**同一个共享 schema**。字段可以按任务增减，但两侧的同一组字段不能单边改名、单边隐藏或换不同的单位：

| 共同字段（两侧标签相同） | 要回答的问题 |
| --- | --- |
| 研究问题／共同目标 | 两边试图解决哪一个同层级问题？ |
| 研究方法 | 两边分别采用了什么方法？ |
| 核心假设 | 为什么认为它会有用？ |
| 学习信号／目标 | 从什么反馈学习，优化什么？ |
| 模型结构／表征／几何 | 采用哪些架构或空间假设？哪些未明确？ |
| 参数更新机制 | 哪些参数如何学习与保存？ |
| 经验载体 | 经验保留在参数、文本、技能还是 Agent 规则中？ |
| 迭代／准入条件 | 下一轮状态如何产生、验收或拒绝？ |
| 证据来源／版本 | 来自论文、代码、计划、运行记录或实验结果的哪一版？ |
| 已验证结论／未知 | 当前能证明什么，不能证明什么？ |
| 可证伪预测 | 什么观测会反驳核心解释？ |

例如 **SEED** 与 **OpenEVO** 两侧都以「研究方法」为字段名；「证据来源」则分别写明可核实的论文、官方实现与项目计划、代码、运行记录。来源类型或成熟度不同可以真实存在，但**不能用两个不同的字段标题偷渡这项区别**。

同一字段若确实无法比较，写明「比较口径不同」并给具体原因；不拼凑相似数字、不将一个侧边的技术强行对应另一侧无关技术。

## 3. 信息与视觉呈现的约束

1. **关系是主角。** 并排用真实比较表或字段同构的双列；序列、反馈、因果、分支、拓扑使用能表达相应关系的语义结构。HTML、图、交互应减少读者推理成本，不是为了装饰。
2. **L0–L3 递进。** 第一屏先说明问题与共同范式；主体清楚展示关键对照；数学和实现细节按需下钻；原始证据可一键追溯。结论所依赖的重要限制不能藏入折叠项。
3. **对齐是内容和视觉的共同约束。** 相同属性的标题、顺序、缩进、字体层级、颜色语义和对应位置应可直接定位。视觉差异必须对应真正的科学差异；相同证据不以不等密度制造虚假强弱。
4. **真实差异不得为了美观被抹平。** 信息缺失、不同阶段、不同预算和不同科研状态必须明确标注。对称是帮助比较的布局，不是伪造同一性的理由。
5. **静态可读、交互可用。** 无 JS、键盘、浅色／深色、长中英文与移动端仍应保留主要逻辑；颜色不独立承担信息。默认移动端验收使用 iPhone 18 Pro Max 440×956 CSS px；页面必须展示完整的比较语义且无不必要的横向拖动。
6. **参考视觉需独立验收。** 当用户要求复刻已认可的 ChatGPT Intelligence UI，分别核对 COPY_MATCH（文字）、TOPOLOGY_MATCH（关系和九组操作）、VISUAL_MATCH（字体／布局／颜色／空间）、BEHAVIOR_MATCH（交互）、SOURCE_IDENTICAL（是否同源代码）。任何一项不能由 CI PASS 或另一项的 PASS 自动推断。

全站色彩、字体、密度、卡片预算、主题和无障碍的权威仍是已有的 [UI design principles](ui-design-principles.md)、[Human-thinking web expression](human-thinking-web-expression-contract.md) 与 [visual acceptance gate](ui-change-visual-acceptance-gate.md)；这里不建立第二套 CSS 规范。SEED × OpenEVO 原始截图和逐项视觉还原状态由 [Flow 专属合同](seed-openevo-flow-intelligence-ui-fidelity.md) 拥有。

## 4. 发布或评审前的验收

**可以机械核验的部分：**

- 两侧同一个字段来自一个共享标签源；共同语义字符串完全相同，不分别改写；
- 共同字段清单、顺序、单位、缺失态在左右两侧一致，且不存在「同左／同上／亦然／见右」式互文；
- 技术层级经过分类，不把训练目标、优化方法、模型架构、几何假设和参数保存错误当作互斥选项；
- 关乎结论的证据边界、未知与版本身份在每边均明确；当前与历史数据不能互换；
- 页内链接、源代码和测试对的是同一份正式内容；实际浏览器能读到它们。

**必须由阅读／证据验收的部分：**

- 不看对面，读者能否各自准确解释 SEED 和 OpenEVO？
- 两边一起看，读者能否区分共同范式、真实技术差异和仅单边具有的能力？
- 对「它相信什么」，能否指出**方法明示的假设**与**我们的推断**的边界？
- 对「它有多可靠」，能否指出论文、代码、实验计划、实际数据的证据层级，而不是凭虚构概率？
- 真实的桌面与 iPhone 18 Pro Max 页面在视觉、交互与内容上是否通过独立检查？

测试通过证明结构约束，不能代替无上下文读者真正理解；读者喜欢一个画面，也不能代替来源核验或浏览器检查。任何仍未验收的维度必须保留 NOT_VERIFIED。
