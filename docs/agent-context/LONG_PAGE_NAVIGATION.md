# Long-page navigation pattern

这是一条长期页面表达规范，供后续编码 Agent 在新增或重构长页面时默认考虑。它来自 PR #137 的实现，但不是一次性 PR 说明。

## 设计意图

当页面很长、章节很多时，不要让读者只能依赖浏览器滚动条判断位置。应在不抢占正文空间的前提下，提供一个轻量的“本页位置地图”，体验接近 Notion 的页面目录或 ChatGPT 长对话旁的定位轨道。

这个组件的职责是**帮助定位和跳转**，不是替代站点主导航，也不是再复制一列完整目录。

## 默认视觉形式

优先使用靠页面右侧悬浮的一列短横线，而不是常驻的大块文字目录。

- 每个主要章节对应一条短横线。
- 当前章节应更明显，例如变长、提高对比度或使用现有强调色。
- 已经经过的章节可以保留较弱的进度状态，但不能比当前章节抢眼。
- 章节名称默认收起，只在 hover、focus 等明确交互时显示。
- 标签应靠近对应横线出现，不覆盖正文，也不造成页面持续占宽。
- 视觉应轻、安静、低干扰；它是阅读辅助，不是主 UI。

如果未来设计系统变化，可以调整具体尺寸、圆角和动画，但应保留“紧凑轨道 + 按需显示标题 + 当前章节反馈”的核心交互模型。

## 信息结构

导航应从页面真实语义结构生成，避免维护第二份目录数据。

当前推荐规则：

1. 从主要内容区域的 `h2` / `h3` 中提取可见标题。
2. 如果有至少 4 个有效 `h2`，优先只显示 `h2`，避免轨道过密。
3. 如果 `h2` 太少，再用 `h3` 补足结构。
4. 已有稳定 `id` 的标题直接复用；没有 `id` 时可以生成冲突安全的锚点。
5. 不应把隐藏内容、dialog、关闭的 details、辅助 UI 标题等误识别为阅读章节。
6. 页面或某个标题如果明确不适合进入导航，应允许通过语义属性排除，而不是写页面名硬编码。

目标是让正文的标题层级成为 single source of truth。

## 何时显示

不是所有页面都应该强行出现悬浮导航。默认只在它真正帮助阅读时启用。

至少满足：

- 页面足够长，明显超过一个普通阅读视口；
- 有至少 4 个有意义的章节；
- 桌面级可用空间足够；
- 不会和页面已有的固定侧栏、工作台面板或关键操作区冲突。

短页面宁可不显示。

## 响应式边界

手机和平板不要把桌面悬浮轨道硬塞进去。

默认行为：

- 桌面宽屏：可以显示悬浮轨道。
- 窄屏、触摸优先设备、较矮视口：隐藏。
- print：隐藏。

如果未来移动端确实需要本页导航，应单独设计适合触摸的形式（例如可展开的章节菜单），不要直接缩小桌面短线轨道。

## 交互规则

- 点击章节后滚动到对应标题。
- 必须考虑 sticky header / site header 的高度，不能把标题滚到顶栏下面。
- 滚动时自动更新当前章节。
- 到达页面底部时，最后一个章节应能正确成为当前项。
- URL hash 可以跟随章节变化或点击更新，但不要造成完整页面刷新。
- hover 不是唯一信息入口；键盘 focus 时也必须能看到章节名称。
- 支持 `prefers-reduced-motion`：用户要求减少动态效果时，不强制 smooth scrolling 或复杂动画。

## 可访问性

这是导航，不是装饰。

- 使用真实 `<nav>` / `<a>` 语义。
- 为导航提供本地化的可访问名称，例如中文“本页导航”、英文 “On this page”。
- 当前章节使用 `aria-current="location"` 或等价语义。
- 每个短线链接即使视觉上没有常驻文字，也必须有可访问名称。
- 键盘用户能完整操作。
- 深色和浅色主题下都要达到足够对比度。

## 与页面表达原则的关系

本项目的长技术页面往往信息密度高。解决办法不是简单把所有内容压缩，而是用 HTML 的结构和交互能力，把“我在哪里、前后有哪些章节、下一步去哪”变成浏览器可感知的界面。

因此后续 Agent 遇到以下情形时，应主动检查是否需要本模式：

- 新增长篇研究页、学习页、复现指南或实验说明；
- 一个页面已经需要大量滚动才能看完；
- 用户反馈“页面太长”“不知道看到哪里了”“来回找章节麻烦”；
- 页面结构已经有清楚的 H2/H3，但缺少快速定位能力。

不要等用户再次逐字提出“做一个像 Notion/GPT 的悬浮导航”。

## 不应该做的事

- 不要为每个长页面手写一套重复目录数组。
- 不要在手机上留下挡正文的小浮条。
- 不要用纯装饰线条却没有真实链接和键盘语义。
- 不要显示几十个同权重节点导致轨道本身变成信息噪声。
- 不要让 tooltip 长时间覆盖正文。
- 不要为了实现目录改变原页面的科学内容或标题语义。
- 不要把组件做成某一个 `/guide/` 页面专属；优先保持共享、语义驱动。

## 当前参考实现

PR #137 引入了当前实现：

- `src/components/PageOutline.astro`
- 在共享 `AppLayout.astro` 中挂载
- 自动读取主要内容中的标题
- 桌面长页面按条件启用
- 当前项、已读项、hover/focus 标签、锚点跳转、sticky header offset、深浅主题、reduced motion 和移动端隐藏均有对应行为

后续可以重构实现，但如果替换组件，应保持本文描述的产品意图与交互边界，除非新的用户需求明确要求改变它。

## 验收清单

修改这一模式时至少检查：

- 长页面会显示，短页面不会误显示；
- 当前章节随滚动正确变化；
- 点击所有节点都落在正确标题附近；
- sticky header 不遮标题；
- hover 与 keyboard focus 都能识别标题；
- light / dark 均清晰；
- reduced motion 可用；
- 手机和触摸布局不挡内容；
- 无重复/冲突 anchor；
- 不引入横向滚动、正文位移或浮层重叠。

这是一项长期 UX 约束：**长页面要给读者位置感，但位置导航本身必须比正文安静。**
