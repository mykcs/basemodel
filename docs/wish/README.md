# 愿望系统

这个目录保存一种和 README、运行手册、设计规范、事故复盘都不同的长期文件：**愿望**。

它回答的不是“代码怎么实现”，而是：

> **这个网站为什么存在？当两种设计都说得通、局部规则彼此拉扯，或者未来的 Agent 已经忘记我们最初为什么这样做时，我们最希望这个网站最终成为什么？**

“愿望”允许变化。变化本身不是失败；真正重要的是始终有一份很短、很清楚的**当前愿望**，同时保留过去愿望被替换的原因。

## 为什么叫“愿望”，而不是再写一份“设计哲学”

“设计哲学”很容易慢慢变成任何网站都成立的套话，例如“简洁、现代、清楚、用户友好”。“愿望”更具体：先回答“我做这个网站到底想帮助自己或读者解决什么问题”，再由设计解释回答“为了实现这个愿望，网站应该怎样组织”。

## 四个文件

### `LATEST.md` — 当前愿望

最重要、最短的文件。保存现在的中心愿望和极少量边界。产品方向、首页角色、信息架构、页面职责或表达方式拿不准时，先回到这里。不要放实现细节、事故、部署状态或通用设计规范。

### `DESIGN.md` — 当前愿望的设计解释

只解释当前愿望怎样推导成这个网站自己的设计。可以按 L0/L1/L2/L3 展开用户情境、网站回应、页面层级和阅读顺序。不要放通用 UI 准则、工程事故、CI/provider/shell/Git 问题、暂时 PR 状态或无关历史。

### `ARCHIVE.md` — 被替换的旧愿望

保存已经不再是当前 authority 的旧愿望，以及它的生效时间、替换时间、当时为什么这样想、为什么后来被替换。默认不读；只有追溯历史意图时才读。

**历史应该可追溯，但不能每天参与投票。**

### `README.md` — 这套机制怎么玩

就是你现在正在读的文件。它定义愿望系统的结构、读取顺序、更新方式和 authority 边界，不保存某一个网站自己的愿望正文。

## Agent 读取规则

```text
小的用户可见文案 / 局部设计
→ 读 LATEST.md

首页、导航、信息架构、页面角色、主要交互、产品方向
→ 读 LATEST.md + DESIGN.md

追溯“以前为什么不是这样”
→ 再读 ARCHIVE.md
```

不要为了仪式感让每个 Agent 每次都读完整 Archive。

## Authority 顺序

```text
当前 owner 明确指令
+ 事实 / 科学 authority / 安全边界 / 可执行真相
        ↓
docs/wish/LATEST.md
        ↓
docs/wish/DESIGN.md
        ↓
具体页面设计与局部实现
        ↓
docs/wish/ARCHIVE.md
```

愿望决定“我们想成为什么”，不能修改“真实发生了什么”。封存实验结果、科学 chronology、证据边界、安全规则和 live provider truth 都不会因为愿望而被重写。

## 更新流程

只有中心思想真的变化时才更新，不要把措辞润色当成一代愿望。

1. 确认这是中心愿望变化，不是局部实现调整；
2. 把旧 `LATEST.md` 的核心内容追加到 `ARCHIVE.md`；
3. 写清日期和替换理由；
4. 更新 `LATEST.md`；
5. 同步更新 `DESIGN.md`；
6. 检查根 `AGENTS.md` 或 Agent router 仍能把未来 Agent 引到这里。

## 不要把这个目录变成杂物间

命令怎么跑属于运行手册；实验真实结果属于科学 authority/evidence；组件怎么实现属于工程文档/源码；事故属于 closeout/history；所有网站都适用的设计原则属于共享设计规范；当前 PR 状态属于 live handoff。

愿望目录只保存**当前中心意图、它的项目特有设计推导，以及已经被替换的旧中心意图**。
