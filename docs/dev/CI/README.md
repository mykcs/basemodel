# CI builds, routing and measured performance

The first phase of BaseModel's CI optimization shipped in [#814](https://github.com/mykcs/basemodel/pull/814), with the risk-gated typography consumer correction merged in [#962](https://github.com/mykcs/basemodel/pull/962). That accepted two-workflow topology built the site twice in GitHub instead of seventeen times and reaches the combined browser-workflow terminal state sooner in the measured sample. **The sampled aggregate Runner time did not decrease.** The current merge/deployment authority remains [hosting architecture](../../agents/current/hosting-architecture.md); this record owns implementation qualification, measurements and rollback.

## Unified automatic graph (candidate qualification)

Public PR CI now owns automatic full acceptance once: one deterministic static build/overflow preflight, Chromium 4 + WebKit 8 duration-balanced shards, and a separate one-case core capture plus six Lab cases. The Cloud Figure workflow is manual only and calls the same reusable graph for explicit full review. Existing `public-ci-gate`, `cloud-figure-chromium`, `cloud-figure-webkit` and typography gate names remain; the required Public gate now waits for both complete engine populations and verified figure artifacts. No branch protection, runner tier, paid resource or Vercel publication policy changes.

The earlier ordinary and expanded figure profiles were not identical: 67 route cases had different reading-state behavior. The unified expanded case therefore runs the exact original light/default assertions at 390/1440 before any reveal or control mutation, then retains all six capture states, grayscale/print images and scientific cell/hash assertions. Complete per-engine discovery and clean first-attempt outcomes must match exactly. The sealer/aggregator/round-trip verifier requires the allocated 4/8 shard total and both default-width proofs for every evidence route. The distinct Public core/Lab population has its own missing/skip/retry/identity failure checks.

Semantic typography work retains full WebKit acceptance, max-failures=0 and seven-day diagnostics even if the ordinary risk result was focused; verified docs skip still allocates zero browsers. Ordinary diagnostics remain three days. Video and trace failure retention are unchanged. The optional preparation token only avoids redundant reading-state reveal after validating target identity, viewport/media/theme and relevant controls; native image decoding, font readiness, clipping, animation handling and screenshot encoding remain. Stale or shopping state reverts to the original preparation. A four-case browser regression tests old/new pixel equality and stale-state repair.

The bounded hosted pilot compared immutable baseline `9982005` and candidate `e9f44b5` on the parameter-memory results WebKit route. Both ran the same application, lockfile, browser image, one-worker/no-retry capture, with matching trace and failure-video settings. Its two runs each passed; 292 PNG files matched byte-for-byte, and the eight new capture-state regressions passed in both Chromium and WebKit. The recorded case durations were 457.1 s and 455.0 s on separate hosted runners. That 2.1-second difference is too small and uncontrolled to claim a repeatable screenshot-helper speedup. The pilot clears the helper correctness gate; topology effects are measured below from complete workflow runs. Prior phase metrics below remain dated historical evidence, not the new topology's performance.

## Previous two-workflow execution (accepted phase one)

Public deterministic validation and Cloud Figure preflight each own one static build. Their browser consumers wait for successful preflight, download only the successful producer's artifact from the same run, then verify head/base/tree, package and lock hashes, Node/npm/Playwright/Astro versions, allowed build environment, producer attempt and every output file's SHA-256. Wrong source, configuration, run, attempt or bytes fail; there is no latest-successful-artifact lookup. Failed-consumer reruns explicitly reuse the successful producer attempt. Vercel still builds its final candidate and Production independently.

The shared planner gives ordinary docs no browser work, bounded pages their mapped Public regression and exact-route smoke, and shared/global/unknown changes the full population. Browser selectors/fixtures, figure evidence gates and timing receipts force full work before route-owner shortcuts. Phone smoke retains iPhone 18 Pro Max browser simulation at 440×956; desktop acceptance and existing specific breakpoint regressions remain.

Cloud Figure runs a lightweight gate on every PR instead of filtering away the workflow. Non-full plans succeed only after successful preflight and an intentionally unallocated/skipped matrix. Full work requires every allocated shard plus exact-population/evidence aggregation. Missing/unknown plans, failed/canceled work, retries and unexpected skips never become success.

Full populations use actual historical browser/profile timings: the longest estimated case is assigned next to the least-loaded shard. Each lane retains all importing specs and selects exact full titles with escaped `--grep`; a second discovery must match the assignment before execution, and clean first-attempt outcomes must match afterward. Unknown cases receive the largest real weight for their browser. The old source-location `--test-list` CLI remains retired because it can lose helper registrations.

Draft heads already run on open and synchronize; changing an unchanged head to Ready does not allocate another full matrix. This was observed on #814: one Public and one Cloud run before and after promotion. Ordinary docs retain `verify:deploy` and the static build, but skip unused artifact transfer and browser discovery.

The semantic `typography` WebKit lane also obeys the shared risk plan. [#962](https://github.com/mykcs/basemodel/pull/962) repairs the consumer's applicability rather than manufacturing an artifact for unnecessary work: no-UI docs allocate no browser, while real typography/UI changes retain all four dedicated WebKit shards. Its always-present gate requires successful planning and deterministic checks, then either a deliberately skipped zero-allocation matrix or successful positive-allocation work. Actual expression/shell tests reject missing allocation, failure and cancellation. The high-risk hosted run and later docs-only hosted run qualify the two runtime paths independently.

## Full-candidate measurements

The historical #957 source differs from the optimized source, and hosted runner speed varies. These are observed samples, not a controlled causal benchmark. The historical figure attempt failed one WebKit lane; the optimized figure run passed both complete populations. Queue time, execution time, deliberate qualification failures and superseded/canceled work must not be mixed into a claim of successful savings.

| Profile | Historical #957 | Optimized #814 | Observation |
| --- | ---: | ---: | --- |
| Public job wall time summed | 3013 s | 2890 s | 50.2 → 48.2 Runner min |
| Public first-job to final gate | 675 s | 685 s | Approximately unchanged |
| Figure job wall time summed | 10034 s | 10836 s | 167.2 → 180.6 Runner min |
| Figure first-job to final gate | 3271 s | 2052 s | 54.5 → 34.2 min |
| Both workflows: workflow created_at to last gate | 3334 s | 2147 s | 55.6 → 35.8 min, about 36% sooner |
| Both workflows: Runner total | 13047 s | 13726 s | 217.5 → 228.8 min, **5.2% higher** |
| GitHub site builds | 17 | 2 | 15 repeated builds removed, about 88% fewer |
| Slowest browser shard | Figure WebKit 2/4, 3265 s (54.4 min) | Figure WebKit 1/4, 1858 s (31.0 min) | Full shard job wall time, including setup |

Runner figures sum actual non-skipped GitHub job `started_at`→`completed_at`, clamping API timestamp inversions to zero; they are not CPU-utilization measurements or exact billed minutes. For failed-only recovery, GitHub creates new job IDs for retained successful jobs while preserving their original timestamps. Across attempt receipts, deduplicate retained execution by `(job name, started_at, completed_at)`, include each genuinely rerun job and failed attempt once, and keep UI-test retry counts distinct from workflow attempts. Queue/workflow-created_at-to-gate time is reported separately. Combined elapsed time starts at workflow `created_at` and ends at the last gate. Vercel deployment builds are counted separately. These samples identify immutable heads/runs/attempts, not the total engineering cost of every task push; no account-wide billing saving or exact commit-push-to-gate clock is claimed. Required Public feedback is roughly eleven minutes in both samples; the major latency improvement is the complete two-workflow high-risk acceptance. For the final #814 head, workflow `created_at` was 15:00:21 UTC, Public gate success 15:11:49 (688 s), exact-head Vercel success 15:22:09 (1308 s), and the final Figure gate 15:36:08 (2147 s). Required checks were therefore green after 21.8 minutes, while this task waited for the complete Figure evidence too. This includes the deliberate delay before requesting Vercel; it is not provider build time. No comparable historical final-Vercel clock is available, so the 36% figure is specifically complete browser-workflow latency, not a claimed 36% improvement in all Required Checks.

Sources: historical [Public 40856964834](https://github.com/mykcs/basemodel/actions/runs/40856964834), [Figure 40856964880 attempt 1](https://github.com/mykcs/basemodel/actions/runs/40856964880/attempts/1); optimized [Public 40897133905](https://github.com/mykcs/basemodel/actions/runs/40897133905), [Figure 40897133931](https://github.com/mykcs/basemodel/actions/runs/40897133931), exact head `0912d7464dafbb46868d2497d0f9468af85c345f`, merged as `126f9e135135cf11995bb58706a272faa83088a5`.

The historical `sitewide-figure-width-scope` file consumed about 35.2 minutes across 106 cases, not one 35-minute test. The largest route cases were about 7.3 minutes for parameter-memory results, 4.9 minutes for bounded effective state and 1.9 minutes for WebShop. Their combined cost was about 40% of that file. The existing [capture helper](../../../tests/e2e/figure-evidence.ts) decodes images, waits for font readiness and animation frames, then captures clipped PNGs with animations disabled; route cases retain their width/theme states plus applicable grayscale and print captures. ## Artifact cost and decisions

On P1 [run 40890621991](https://github.com/mykcs/basemodel/actions/runs/40890621991), the Public build took 21 seconds, its 10.4 MB ZIP uploaded in 3 seconds, eight downloads totaled 15 seconds, and verification totaled 3 seconds. At that producer's speed eight extra builds would cost 168 seconds versus about 21 seconds for sealing, transfer and verification; this is a build-stage accounting estimate, not a controlled eight-build replay. The final Public producer built in 26 seconds and uploaded in 3 seconds.

The accepted phase-one topology retained two independent build owners. Combining them merely to save the second measured 26-second build offers less than 0.2% of the sampled total Runner time, while coupling source/artifact provenance and the separate ordinary/deep-figure acceptance roles. No cross-workflow token/run-discovery path was added in that phase. Plain UI and full figure capture have different screenshot workloads and execution budgets; one green run is not substituted for the other.

P1 alone saved job time but increased Public elapsed time: 3013→2774 job seconds and 675→777 elapsed seconds. An intermediate P2 Public sample observed 2687/625 seconds, while the final candidate observed 2890/685. Reporting only the best intermediate result would overstate the outcome. The confirmed benefits are fewer build executions, shorter full-matrix latency, no unchanged Ready-promotion replay and early rejection of invalid candidates. A net reduction of all successful-run compute remained unproven for phase one.

## Rollback

Revert workflow, scheduler/risk owner and matching contract changes together through a normal PR. Keep `public-ci-gate` and Vercel protection active; never remove required contexts to undo the optimization. Restoring native per-shard builds/scheduling restores their original cost. Preserve timing receipts, intentional-failure records and real source identities rather than rewriting historical measurements.
